## Question and scope

Extend RQ3 to ask how a Claude model and a locally served Gemma model compare with the existing GPT-6 Sol and GPT-6 Luna summaries **on the same 36 education bills**. Keep the nine method-development pilot bills excluded. Use one new summary per bill per new model: **72 new summaries**. Treat this as an exploratory cross-provider and local-versus-hosted comparison, not a randomized estimate of corporate or model-family superiority.

## Fair comparison procedure

1. Reuse the frozen [sample manifest](../data/full/sample.json), exact as-filed `bill_text`, and [approved summary instruction](../prompts/pilot-summary-v1.txt). Use the same one-field `summary` JSON schema where supported. Provider-specific API envelopes may differ; save those envelopes and settings rather than claiming identical decoding controls. Do not manually rewrite a model's summary. A malformed or truncated output is a pipeline failure to log and resolve under a prespecified retry rule, not a low substantive score.
2. Before the scored run, check API access and the local server. Test the adapters and schema on a small **unscored feasibility set drawn from the existing nine pilot bills**, including a long bill, and verify the local model's loaded context can hold the full source, instruction, and output. Freeze any adapter or output-format adjustment before the 36-bill run. Keep these checks separate from the 36-bill results.
3. Run each new model once per bill with no outside sources, tools, retrieved documents, or conversational history. Save raw request/response, date, exact source and prompt hashes, model ID, model/provider and runtime version, output schema, decoding settings, response status, token usage where available, and the unedited parsed summary. For Gemma also save the model file/hash or other stable identifier, quantization, loaded context length, and LM Studio version. Record cost for paid calls and elapsed time separately from quality outcomes.
4. Apply the existing pinned readability formulas and whitespace compression rule to all new source-summary pairs. Reuse the **same source-only Astra proposition inventories** already generated for the 36 bills, and apply the frozen v2 coverage and factuality instructions to each new summary. This requires **144 additional Astra assessments** (36 bills × 2 new models × coverage and factuality), with no new source-inventory calls. Reuse the versioned quote validator uniformly; preserve raw evidence and failures. Do not revise Astra's inventory based on the new outputs.
5. Compare all four models **within each bill**, overall and within the original short/medium/long strata. Keep linguistic complexity, core/supporting coverage, factual consistency, and compression separate. Report both bill-weighted fractions and pooled proposition/claim denominators; claim counts may differ by model. Show descriptive paired differences and individual examples, without a composite quality score or a universal model ranking.
6. If the researcher sanity check is extended, use the **same three bills selected before the original generation** (HB1228, HB0187, HB0522). Sam would inspect the six new Claude/Gemma summaries against source text for factual accuracy, material omission, and substantive-meaning change **before viewing their Astra judgments**. Retain the original six logs separately. Because the researcher may already know the prior Astra findings for these bills, describe the extension check as limited and only partially blinded; do not claim independent expert validation or inter-rater reliability.

## Feasibility gates and interpretation limits

- Sam confirmed Claude Console API access and added `ANTHROPIC_API_KEY` to the ignored `.env`. Access to `claude-sonnet-5-5` was verified without exposing the key. Claude [documents separate Console/API billing](https://support.claude.com/en/articles/9876003-why-is-claude-api-usage-billed-separately-from-my-paid-claude-plan). Manual copying through the chat app would omit important request controls and logs, so it should not be pooled with the scripted 36-bill comparison.
- LM Studio [supports a local server](https://lmstudio.ai/docs/developer/core/server) and [JSON-schema output through its compatible chat endpoint](https://lmstudio.ai/docs/developer/openai-compat/structured-output). The server exposes the exact `google/gemma-4-31b-qat@q4_0` configuration. It was reloaded at **16,384 context tokens**, with the old and new settings recorded. Gemma's default reasoning consumed a small output cap without producing a summary in one pilot check; the fixed extension configuration is explicit `reasoning_effort=none` with an **8,192-token output cap**, validated on the long-tail pilot bill. This is a configuration limitation, not a claim about Gemma's reasoning-enabled performance.
- Keep GPT-6 Astra as the **single common automated evaluator** to avoid changing the completed evaluation method. Its OpenAI provenance may influence comparisons with Claude and Gemma, and its judgments are not human ground truth. The three-bill researcher check cannot estimate this bias or an error rate.
- Prompt and output-format compatibility, model size, quantization, context allocation, and provider defaults may affect differences. Attribute observed results to these exact configurations rather than to entire corporations or model families. No inferential significance claim is planned for 36 exploratory bills.
