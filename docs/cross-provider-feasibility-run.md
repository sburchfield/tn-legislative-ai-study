# Cross-provider generation feasibility record

**Run date:** November 2, 2026. **Scope:** Three unscored bills from the original nine-bill method-development pilot: HB2329 (short, 70 source words), HB1772 (medium, 386), and HB1732 (long tail, 2,135). These are **not** among the 36 full-experiment results. The [proposal](cross-provider-extension-proposal.md) and [adapter](../scripts/extension/check_generation_feasibility.py) define the prospective extension. No Astra evaluation or new full-sample generation was performed.

The read-only Claude Models API check confirmed that `claude-sonnet-5-5` is accessible. The three requests used the existing frozen corpus, pilot bill hashes, `prompts/pilot-summary-v1.txt` (SHA-256 `a8a84c7d3640ce11249e107717a11e24499592c70f24dc2215bc9305b9949889`), and one-field schema (SHA-256 `65ee03d0a90267593885b0982684a55a9d7f7d40e7ce2a505d3c3c663a72b3a1`). Its local model metadata reported the selected `@q4_0` variant, default reasoning `on`, a maximum supported context of 262,144, and an **initially loaded context of 8,192 tokens**. The downloaded instruction-tuned GGUF `gemma-4-31B-it-QAT-Q4_0.gguf` has SHA-256 `6f63619c9e33826a2a8ab195a344c79ecae7c82341d5567e28fd8863df056a7b`. Local requests used `/v1/chat/completions` with the same system/user text and a one-field JSON schema. The task's ordinary network sandbox blocked even localhost; narrow escalated network access was used for these local calls and Claude calls.

The first Gemma check used its default reasoning mode with a 1,024-token output cap. HB2329 completed, but HB1772 exhausted all 1,024 tokens with **1,018 reasoning tokens and no summary** (`finish_reason=length`). The exact completed short response and the non-scorable medium response were preserved in [`prior_attempts/`](../data/extension/feasibility/gemma/prior_attempts/). A separate trivial local probe showed that `reasoning_effort=none` on LM Studio's schema-constrained chat endpoint yields valid JSON with zero reasoning tokens. The adapter was changed to send that explicit setting, and all three pilot checks were rerun with a 2,048-token cap. No earlier response was silently replaced or scored. The probe also showed that the local `/v1/responses` endpoint ignored the supplied JSON schema in that test, so the schema-constrained chat endpoint was retained.

The 8,192-token loaded context was too close to the longest full-study inputs for the originally allowed output cap. The Gemma instance was then unloaded and reloaded at **16,384 tokens**, preserving the earlier and verified new configurations in [`data/extension/local-model-load.json`](../data/extension/local-model-load.json). The first long-tail check at 8,192 context and 2,048 output cap was moved to `prior_attempts/`. A new HB1732 check with **16,384 context, explicit `reasoning_effort=none`, and the intended 8,192-token output cap** completed with `finish_reason=stop`, 4,515 prompt tokens, 244 output tokens, and zero reasoning tokens. The exact returned model ID and JSON schema passed validation. This supports using that fixed Gemma configuration for the scored run; the longest 36-bill source must still receive a preflight context check.

These calls check transport, output format, model identity, and gross context behavior. They are **not comparative quality results**. Claude's 71-word HB2329 summary was slightly longer than the 70-word source despite the shared compression instruction; this remains an observed outcome rather than a reason to tune the prompt. The Gemma success with reasoning off does not show how it would perform with reasoning on. Provider-specific effort controls are not equivalent across models and must be reported as a limitation. No full-sample extension generation or Astra extension audit has begun.
